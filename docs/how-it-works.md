# Как это работает, простыми словами

Это курсовой проект по многоагентным системам.
Тема - проверка политических утверждений, примерно как на PolitiFact, только автоматически.
Сейчас готов первый этап: два агента, которые делают разные вещи и передают друг другу результат.
Полная схема из семи ролей лежит в `ARCHITECTURE.md`, здесь только то, что уже работает.

## Что происходит после кнопки «Запустить»

Я ввожу утверждение, например «Each year, 18,000 people die in America because they don't have health care», и, если знаю, кто это сказал.

Дальше работает раннер.
Это обычный код без нейросетей: он создаёт запись о запуске, запоминает лимиты (не дольше двух минут, не больше восьми вызовов) и по очереди отдаёт работу агентам.
В терминах ТЗ это оркестратор, и он специально сам ничего не анализирует.

Первый агент - аналитик.
Он идёт в языковую модель через OpenRouter и просит сделать из текста один проверяемый тезис: убрать воду, вытащить имена, числа, даты, тему и предложить два-три поисковых запроса.
Ответ должен быть строго в JSON по схеме.
Если модель вернула мусор, аналитик один раз показывает ей ошибку и просит исправить, после второй неудачи запуск честно завершается с ошибкой.

Второй агент - классификатор.
Он получает от аналитика не исходный текст, а готовый тезис, то есть сообщение Analysis.
Сначала он ищет спикера в датасете LIAR: партия, должность, штат и сколько раз PolitiFact уже ловил человека на неправде.
Потом прогоняет тезис и эти данные через мою дипломную модель (RoBERTa плюс ветка метаданных) и получает вероятности по шести классам, от pants-fire до true.
Его ответ - сообщение Prediction, в нём есть ссылка на сообщение аналитика, так что цепочку видно целиком.

В конце раннер сохраняет итог, а страница показывает оба сообщения, вероятности и журнал: кто, что и когда вызвал и сколько миллисекунд это заняло.

## Зачем два агента, если можно было одним промптом

Потому что задачи разные по природе.
Выделить тезис - языковая задача, тут нужна LLM.
Оценить правдоподобие - задача классификации, для неё у меня есть обученная модель, которая знает историю спикеров.
LLM про историю конкретного человека на PolitiFact ничего надёжного не знает, а моя модель не умеет читать длинный текст и вытаскивать из него утверждение.
Когда роли разделены, каждого можно заменить отдельно, а в журнале видно, кто именно ошибся.

Наглядный пример - фраза Трампа про нелегальных иммигрантов: «could be 3 million, it could be 30 million».
Без данных о спикере модель склоняется к mostly-true, с его историей на PolitiFact выдаёт false.
Эталон в LIAR - pants-fire, то есть метаданные тянут ответ в правильную сторону.
Сама модель слабая, macro-F1 около 0.3, но для шести классов LIAR это обычный уровень, и здесь она только один из сигналов.

## Важная оговорка про модель

Модель из диплома не знает фактов.
Она училась на десяти тысячах коротких заявлений американских политиков с оценками PolitiFact и ловит две вещи: как сформулировано утверждение и какая репутация у спикера.
Поэтому на фразу «Eiffel tower was built in 2015» без спикера она даёт почти ровное распределение, где mostly-true побеждает на пару процентов.
Это не ошибка кода, а предел модели: вне американской политики и без истории спикера её ответ близок к случайному.

Чтобы это не вводило в заблуждение, аналитик отдельно отмечает, попадает ли утверждение в область модели.
Если нет, страница показывает оценку приглушённо и прямо пишет, что это не вердикт.
Настоящая проверка фактов появится со следующими агентами: поиск доказательств и сборка вердикта со ссылками на источники.

## Почему оно не зависнет и не соврёт про ход работы

Каждый вызов LLM или инструмента проходит через одну и ту же функцию.
Она проверяет, не вышло ли время, считает шаги, меряет длительность и пишет строку в SQLite.
Ключи лежат только в `.env`, в журнал они не попадают.
Пустой или слишком длинный ввод отклоняется ещё до запуска агентов.
Если нет файла модели или провайдер недоступен, запуск заканчивается статусом failed с понятной причиной, а не висит.

Журнал одного запуска можно скачать в JSONL.
Это и есть доказательство распределения нагрузки по агентам из ТЗ.
Пока агентов два, у классификатора 67 % вызовов, порог в 40 % имеет смысл только для полной системы из пяти и больше агентов.

Те же вызовы параллельно уходят в Langfuse, там это дерево: запуск, внутри два агента, внутри них вызов модели и инструменты.
Удобно для разбора, но не обязательно: без ключей трейсинг просто выключен.

## Что где лежит

`app/agents.py` - два агента, по классу на каждого, у каждого один метод `run`.
`app/runner.py` - раннер и лимиты.
`app/messages.py` - форматы сообщений, это pydantic-модели.
`app/llm.py` - клиент OpenRouter, любая модель задаётся строкой.
`app/tools.py` - загрузка дипломной модели и справочник спикеров LIAR.
`app/store.py` - SQLite: запуски и события.
`app/server.py` и `app/static/index.html` - API и страница.
`tests/` - восемь тестов, работают без сети и без файла модели.

## Что дальше

По плану ещё четыре агента: поиск доказательств в вебе, оценка источников, сборка вердикта и независимая проверка результата с одним кругом исправлений.
Раннер к этому готов: добавить агента значит написать класс с методом `run` и вставить его в очередь.
